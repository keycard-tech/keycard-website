# Pinless signing

<Admonition type="caution">
  **Removed in 4.0.** Every signature now requires a verified PIN over an open
  secure channel. Applet 3.x cards are still in the field and cannot be
  upgraded, so this page stays for clients that must support them — but do not
  build new features on pinless signing.
</Admonition>

## Why it was removed

The feature let a card sign with one fixed BIP-32 path with no PIN and no secure channel, on the theory that the wallet assigned to it holds only pocket money. In practice that assumption was hard to enforce: whoever got hold of a card could drain that path forever, with no way for the owner to notice, and the "just pocket money" path was set by a different piece of software than the one spending from it.

The payment flows it was designed for are better served by a [Keycard Shell](/developers/diy-keycard-shell), where each signature is confirmed on the device's own screen — which bounds the damage the same way, without trusting the host.

## Specification (applet 3.x)

Signing using the pinless path can be done without opening a Secure Channel. Since in such a scenario no sensitive data is being transferred, the reasoning was that neither encryption nor authentication was needed.

### Defining a pinless path

Defining which path is used for pinless signing requires PIN authentication and thus a Secure Channel. This means only the owner can define which wallet is allocated for this operation. The SDK call is

```java
cmdSet.setPinlessPath("m/44'/0'/0'/0/200").checkOK();
```

### Signing with pinless path

When a pinless path is defined, a wallet (or POS terminal) can invoke `signPinless` without knowing the path. If no pinless path was defined, the Status Word 0x6A88 is returned. Opening a Secure Channel and authenticating with the PIN before sending this command is allowed but not necessary.

```java
cmdSet.signPinless(hashToSign).checkOK();
```

### Alternatives on 4.0

* For unattended signing where the service must not hold the key, use a Shell and its on-device confirmation step.
* Where a device genuinely cannot prompt for a PIN, keep the value in the account low and treat the path as public — the same advice applied here before, but the card no longer pretends to enforce it.
