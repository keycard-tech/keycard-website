# EXPORT KEY

* CLA = 0x80
* INS = 0xC2
* P1 = ignored since 4.0
* P2 = export options
* Data = a sequence of 32-bit integers (most significant byte first). Empty for the master key.
* Response SW = 0x9000 on success, 0x6A86 if P2 is invalid
* Preconditions: Secure Channel must be opened, user PIN must be verified, a valid keypair must be loaded

P2:
* 0x00 = private and public key
* 0x01 = public key only
* 0x02 = extended public key only (public key + chain code)

Response Data format:
- Tag 0xA1 = key template
  - Tag 0x80 = ECC public key (if P2 = 0x01 or 0x02)
  - Tag 0x81 = ECC private key (if P2 = 0x00)
  - Tag 0x82 = chain code (if P2 = 0x02)

Exports the key at the given path. The path is always taken from the data field; since 4.0 nothing is made "current", so the same command is used both to read a key and to leave the card state untouched.

## What can be exported

Transaction-signing keys never leave the card. Only the public key can be exported for an arbitrary path. Private key export is restricted to paths under the [EIP-1581](https://eips.ethereum.org/EIPS/eip-1581) subtree (`m/43'/60'/1581'…`, at least 5 components deep), which by design are not used for transactions.

The extended public key (`P2 = 0x02`) additionally returns the chain code, which allows non-hardened child public key derivation on the host. It is refused for EIP-1581 paths and, since 4.0, for the master key: exporting the master chain code would let the holder derive every non-hardened descendant of the wallet, so the deepest allowed path is one level below master.

## Version note

Before 4.0, P1 selected the derivation behaviour: `0x00` exported the current key, `0x01` derived without changing it and `0x02` derived and made the path current. Since there is no current path anymore, P1 is ignored. The master key can no longer be exported as an extended public key.
